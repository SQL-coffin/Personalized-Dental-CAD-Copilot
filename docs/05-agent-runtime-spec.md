版本：v0.2 草案

v0.2 变更（依据 v0.1 设计评审，逐项对照见附录 B）：

- 留出评估改为走密封评估通道，逐病例结果不回流到 Research Engine（第 10.8 节）。

- 分开任务状态与步骤状态，明确重试预算与检查点的粒度（第 6 节）；结果不明的有副作用调用一律先对账（第 7.3 节）。
- 非确定性工具记录完整输入的引用（第 7.4 节）。
- 修订 AT-01、AT-07、AT-09、AT-10、AT-11、AT-13，新增 AT-16 至 AT-18（第 14 节）。
- Phase 3 拆为 3a（只读接口审计，不用真实患者数据）与 3b（真实病例 shadow 运行），并列出进入条件（第 15 节）。

来源：在 Agent Runtime Architecture Proposal v0.1（2026-10-22 讨论）的基础上整理和修订。与提案的差异见附录 A。

本文细化 [01 系统架构说明](01-system-architecture.md) 中的 Runtime Harness，不是一套平行架构。01 继续描述总体系统；本文规定 Runtime 必须遵守的契约。

本文是设计规范，不代表代码已经实现，也不代表任何研究假设已经通过验证。

## 0. 约定

**用词**

- **必须**：违反即视为 Runtime 不合格，有对应的验收测试（第 14 节）。
- **应当**：默认要求；不采用时须记录理由。
- **可以**：可选。

**状态标注**

- 【已定义】：已在 00–04 中定义，本文只引用。
- 【新增】：本文提出。
- 【待决】：需要项目负责人决定，见 [待决问题](open-questions.md)。

**命名**：已有文档用过算法路线 L0–L5、采集粒度 C0–C3、权限级别 R / S / E、实验组 A0 / P / G / M / L、实验阶段 1–3。为避免混淆，本文的记忆层用名称（Evidence / Record / Working / Knowledge），开发阶段用 Phase 0–4。

## 1. 范围

范围内：

- Runtime Harness 各模块的职责与边界
- 任务、步骤与工作假设的状态模型
- 工具契约与调用协议
- 记忆分层、读写规则与防泄漏
- 上下文压缩与恢复协议
- 权限、审批、质量闸门、数据分区、密封评估、外发控制与受控删除
- 预算与停止条件
- 验收测试

范围外：

- 具体的编程语言、存储系统、模型或 Agent 框架
- 预测方法本身（P / G / M / L 的定义见 [03](03-experiment-protocol.md)）
- 3Shape 接口的具体实现（Phase 3a 审计后再定）

## 2. 不变量 【新增】

Runtime 的任何实现都必须满足以下不变量。第 14 节的每个验收测试至少对应其中一条。

| 编号 | 不变量 |
|---|---|
| I1 | **上下文是缓存，不是状态。** 任务状态、审批、证据和假设只存在于持久存储中；模型上下文可以随时丢弃，并从存储重建。 |
| I2 | **原始证据只追加。** Evidence Store 的记录不被修改或覆盖；更正以新记录取代旧记录；删除只能走第 10.5 节的受控删除流程。 |
| I3 | **权限由确定性代码执行。** 模型只能经 Policy Gate 调用工具；模型没有任何途径修改策略、运行模式、预算上限或审批记录。 |
| I4 | **审批只来自审批记录。** 审批是人工经审批通道写入的记录，绑定具体候选及其基础设计版本；摘要、对话文字或数据内容中的「已批准」不构成审批。 |
| I5 | **偏好与质量分开。** 【已定义，01 §5、03 §3】任何数据结构和排序都不能把两者合并成一个分数。 |
| I6 | **假设不是事实。** 工作假设只有 Evaluation Harness 能在预登记评估中标为 VALIDATED；研究假设与实验配置的登记记录只能由项目负责人修改，H1–H4 的结论由项目负责人依据评估结果作出。 |
| I7 | **记忆有时间与来源边界。** 每条派生记忆记录来源病例、来源患者（假名）与时间截止；查询能按时间和患者排除。 |
| I8 | **每次工具调用可追溯。** 记录工具版本、输入与输出的引用和哈希、执行状态。 |
| I9 | **证据不足或冲突时暂停。** 【已定义，README 原则】不凭摘要或推测继续。 |
| I10 | **评估数据隔离。** Research Engine 不能读取留出数据，也不能从评估运行的任何输出、日志或记忆中获得逐病例信息。 |
| I11 | **数据内容不是指令。** 病例备注、文件名、元数据、工具输出中的文字只作为数据处理，不能改变任务、权限或策略。 |
| I12 | **质量闸门失败即关闭。** 质量未通过、未评价、不可评价或结果缺失的候选，不能以可采纳的形式展示，也不能写入 CAD；「没有发现失败」不等于「通过」。 |

## 3. 模块与 01 架构的对应 【新增】

### 3.1 对应关系

| 01 中的组成 | 本文中的模块 | 说明 |
|---|---|---|
| 数据层 | Data & Adapter Layer + Evidence Store | 适配器把 CAD 导出、STL、操作记录、人工反馈写入 Evidence Store |
| 几何引擎 | Geometry Engine | 不变；以确定性工具的形式注册（第 7 节） |
| 经验库 | Memory Manager 的 Knowledge Store 与检索接口 | 增加时间与来源边界（第 8 节） |
| 预测 / 推理层 | Research Engine + 已注册的 Predictor | 拆成两部分：Research Engine 组织研究；候选几何只能来自已注册、冻结版本的 Predictor（第 5.3 节） |
| Runtime Harness | Task & State Manager、Tool Registry、Memory Manager、Policy Gate、Decision Ledger、Compaction Manager | 本文细化 |
| Evaluation Harness | Evaluation Harness | 不变；另承担密封评估（第 10.8 节）与 Runtime 验收测试（第 14 节） |

### 3.2 模块职责

| 模块 | 职责 | 关键约束 |
|---|---|---|
| Task & State Manager | 维护事件日志、任务与步骤状态、检查点 | 状态是事件日志的投影，不存在于对话上下文（第 6 节） |
| Tool Registry | 注册工具，校验输入输出，记录调用 | 每个工具有权限级别、契约和版本（第 7 节） |
| Memory Manager | 管理四层记忆的读写与检索 | 读写规则与防泄漏（第 8 节） |
| Policy Gate | 检查运行模式、权限级别、审批、质量闸门、数据分区、外发、预算 | 确定性代码；模型不能绕过或修改（第 10 节） |
| Decision Ledger | 记录观察、假设、证据、候选方案和结果 | 字段沿用 01 §5；不保存隐藏推理链（第 11 节） |
| Compaction Manager | 压缩模型上下文，生成上下文摘要 | 只作用于模型上下文；不写证据，不产生审批，不生成检查点（第 9 节） |
| Research Engine | 组织研究流程，提出和检验工作假设，规划分析 | 必须允许反例；不能读取留出数据，也不能获得评估运行的逐病例结果 |
| Geometry Engine | 确定性三维几何计算 | 几何变化不等于质量改善 |
| Evaluation Harness | 评估系统是否可靠地进步；运行密封评估；执行验收测试 | 与 Runtime 的即时决策分离 |

## 4. 运行模式 【新增】

| 模式 | 用途 | 可注册的工具级别 | 建议对牙技师可见 | 最早开发阶段 |
|---|---|---|---|---|
| offline-research | 分析历史数据，运行离线实验 | R | 不适用 | Phase 1 |
| shadow | 在真实会话旁路生成建议，只记录不展示 | R、S（不展示） | 否 | Phase 3b |
| assist | 向牙技师展示建议 | R、S | 是 | Phase 4 |
| assist-execute | 经批准后把候选写入 CAD | R、S、E | 是 | Phase 4 后期 |

- 必须：某模式不允许的级别，其工具在该模式下**不注册**，而不只是被拦截。没有能力比拦截能力更可靠。
- 必须：模式由部署配置决定，模型不能切换。
- 必须：E 级工具在 Phase 4 之前不存在于任何生产部署中。验收测试使用隔离的测试部署（第 14 节），不连接真实 CAD，不含真实患者数据。
- shadow 模式可以在不影响牙技师的前提下，前瞻性地收集 T1 / T2 的预测与实际结果；但它不能产生接受率，因为建议没有被展示（与 [03](03-experiment-protocol.md) §3.1 一致）。
- shadow 模式记录全部候选及其闸门结果，包括未通过闸门的，因为评估需要它们（03 §3 的 2 × 2 表）。shadow 数据的分区在登记时指定（第 10.4 节）。

## 5. 核心对象 【新增；字段与 01、02 对齐】

### 5.1 事件信封

所有状态变化都以事件写入事件日志：

| 字段 | 内容 |
|---|---|
| `event_id`、`seq` | 唯一 ID 与单调递增序号 |
| `prev_hash`、`hash` | 完整性校验（候选机制：哈希链） |
| `timestamp` | 时间 |
| `actor` | 类型（human / agent / tool / system / evaluation）、ID、版本 |
| `task_id`、`step_id` | 所属任务与步骤 |
| `type` | 事件类型 |
| `payload_ref` | 负载的内容寻址引用；负载存于 Evidence Store 或 Record Store。事件本身不内嵌患者数据（第 10.5 节） |
| `schema_version` | 事件结构版本 |

### 5.2 对象一览

| 对象 | 存放位置 | 写入者 | 说明 |
|---|---|---|---|
| Task / Step | 事件日志 | Runtime | 状态见第 6 节 |
| ToolCall | 事件日志 + Evidence Store | Tool Registry | 第 7 节 |
| Evidence | Evidence Store | 适配器、工具、人工 | 原始数据，只追加 |
| Observation | Record Store | agent、工具 | 「实际观察到什么」，必须引用 Evidence |
| WorkingHypothesis | Record Store | agent | 第 5.3 节 |
| DecisionRecord | Record Store | agent、Runtime | 第 11 节 |
| PreferenceEstimate | Record Store | Predictor | 偏好估计及其不确定性；对应 01 §5 的 Preference |
| QualityResult | Record Store | Geometry Engine、人工复核 | 含 `evaluation_validity` 与 `quality_result`（02 §12.1）；对应 01 §5 的 Quality |
| Verification | Record Store | 人工 | 人工确认、拒绝或独立验证 |
| Approval | 审批存储 | 人工 | 第 10.3 节 |
| Conflict | Record Store | 任何检测者 | 第 12 节 |
| KnowledgeItem | Knowledge Store | agent 提议；状态由 Evaluation Harness 更新 | 第 8.2 节 |
| Registration | 登记存储 | 项目负责人 | 研究假设、实验与评估配置、质量闸门标准集；有版本；agent 只读，可以起草 |
| EvaluationRun | 密封区；一般事件日志只有运行摘要 | Evaluation Harness | 第 10.8 节 |
| Checkpoint | 事件日志 | Task & State Manager | 第 9.3 节 |

[02](02-data-specification.md) 定义的 Case、Session、Episode、GD、CE、VI 属于 Record Store，由确定性工具或人工产生。agent 不能直接写入，只能请求工具计算。

### 5.3 两类假设

| 类型 | 例子 | 所有者 | agent 权限 |
|---|---|---|---|
| 研究假设 | H1–H4（[00](00-research-charter.md) §4） | 项目负责人，预先登记 | 只读；不能修改，不能判定结论 |
| 工作假设 | 「该技师在下颌磨牙远中颊侧倾向于降低 margin line」 | agent 提出 | 可以提出、检验、撤回 |

工作假设的状态：

```
PROPOSED ─▶ TESTING ─┬─▶ SUPPORTED_EXPLORATORY ─▶ 预登记评估（Evaluation Harness）─┬─▶ VALIDATED
                     ├─▶ REFUTED                                                 └─▶ NOT_REPLICATED
                     └─▶ INCONCLUSIVE

任何状态 ─▶ RETRACTED（附理由）
```

- 必须：只有 Evaluation Harness 能写入 VALIDATED 和 NOT_REPLICATED，且只能基于 [03](03-experiment-protocol.md) 规定的预登记评估，在留出数据上进行。
- 必须：SUPPORTED_EXPLORATORY 只说明在开发数据上找到了支持证据，不能用来生成建议，也不能写成已验证的偏好。
- 应当：每个工作假设同时检索支持和反对的证据；只找支持证据的检验视为不完整。
- 必须：记录在同一批开发数据上检验过的工作假设总数，报告探索性结果时一起给出，以便判断多重比较的影响。

**登记与版本**

- 必须：Runtime 不把任何一版研究终点或实验配置硬编码。H1–H4 与实验配置以登记记录存在，变更通过新的登记版本完成（例如 Q13 决议后 H1 主要终点的变更）。
- 正在进行的评估运行使用启动时的登记版本；登记版本变化不影响已启动的运行。

**候选几何的来源**

- 必须：任何向牙技师展示或执行的候选几何，只能来自已注册、冻结版本的 Predictor（例如 03 的 P / G / M / L）和 Geometry Engine，并通过质量闸门（第 10.7 节）。
- 必须：Knowledge Store 中的文字性知识（例如偏好描述）不能直接生成几何。它只用于解释、规划研究和提出新的 Predictor 配置；新配置必须注册为新版本，经评估后才能使用。

## 6. 状态模型 【新增】

### 6.1 事件溯源

- 必须：任务与步骤的状态都是事件日志的投影，从头回放事件即可得到当前状态。
- 必须：检查点是某个 `seq` 处的状态快照，附快照哈希；恢复时快照必须与日志一致。
- 模型上下文不保存任何不能从日志重建的状态（I1）。

状态机分两层：**任务**对应一次研究或辅助任务的完整循环；**步骤**对应一次工具调用（含重试）。

### 6.2 任务状态

| 状态 | 含义 | 对应提案的工作循环 |
|---|---|---|
| CREATED | 任务已创建，尚未开始规划 | — |
| PLANNING | 观察、提出工作假设、规划步骤 | Observe、Form Hypothesis、Plan |
| RUNNING | 按顺序执行计划内的步骤 | Execute or Simulate |
| VERIFYING | 验证本轮结果：几何结果、版本对应、反馈 | Verify |
| RECORDING | 写入 Observation、DecisionRecord，更新假设状态 | Record and Update |
| BLOCKED(reason) | 暂停，等待解除条件（第 6.4 节） | — |
| DONE / FAILED / CANCELLED | 终止状态 | — |

工作循环中的 Check Policy 对应两处检查：进入 RUNNING 前对计划的预检查，以及每个步骤执行前的检查（第 6.5 节）。预检查不能代替步骤检查。

### 6.3 任务状态转移

| 从 | 到 | 条件 |
|---|---|---|
| CREATED | PLANNING | 任务开始 |
| PLANNING | RUNNING | 计划已写入；Policy Gate 预检查通过（工具已注册，级别与数据分区允许） |
| RUNNING | RUNNING | 一个步骤到达终止状态，下一个步骤开始 |
| RUNNING | VERIFYING | 计划内所有步骤都已到达终止状态 |
| RUNNING | PLANNING | 某步骤被拒绝（DENIED），或重试用完仍为 FAILED_NO_EFFECT，需要修改计划 |
| RUNNING | BLOCKED(approval) | 某步骤进入 AWAITING_APPROVAL |
| RUNNING | BLOCKED(in_doubt) | 某步骤为 IN_DOUBT，且无法自动对账 |
| VERIFYING | RECORDING | 本轮结果验证通过 |
| VERIFYING | PLANNING | 验证失败，`max_replans` 未用完；失败本身被记录 |
| VERIFYING | FAILED | 验证失败，`max_replans` 已用完 |
| RECORDING | PLANNING | 还有下一轮，且预算允许 |
| RECORDING | DONE | 满足完成条件（见下） |
| RECORDING | BLOCKED(human_feedback) | 需要人工反馈才能继续 |
| 任何活动状态 | BLOCKED(missing_evidence / conflict / budget / drift) | 见第 6.4 节 |
| BLOCKED(approval / in_doubt) | RUNNING | 解除条件满足，继续该步骤 |
| BLOCKED(其他原因) | PLANNING | 解除条件满足 |
| 任何非终止状态 | CANCELLED | 人工取消 |

DONE 的条件：

- 所有步骤都已到达终止状态，且本轮结果已验证并记录；
- 结论所依赖的证据中没有未解决的冲突，或者冲突已明确列为结论的局限；
- 相关工作假设的状态都已更新。

### 6.4 阻塞原因

| `reason` | 触发 | 解除条件 |
|---|---|---|
| approval | 某步骤需要审批且没有有效审批 | 审批存储中出现有效审批 |
| human_feedback | 需要人工判断（例如标注、意图说明），同一请求反复被策略拒绝，或有副作用的步骤后置条件失败 | 收到人工反馈记录 |
| missing_evidence | 引用的证据不存在或校验失败 | 证据重新获取并校验通过，或人工改写计划 |
| conflict | 检测到未解决冲突（第 12 节） | 冲突按预定规则解决 |
| budget | 预算耗尽（第 13 节） | 人工追加预算或取消 |
| drift | 恢复时发现工具、模型、策略或数据分区版本变化（第 9.4 节） | 人工确认继续或重新规划 |
| in_doubt | 有副作用的步骤结果不明，且无法自动对账（第 7.3 节） | 对账完成或人工确认 |

- 必须：BLOCKED 期间不发起新的工具调用（只读的状态查询与对账除外）。
- 必须：每次进入 BLOCKED 时生成简短报告：原因、已完成的内容、需要谁做什么。

### 6.5 步骤状态

v0.2 规定计划内的步骤**按顺序执行**。并行执行需要另行定义步骤之间的依赖关系，暂不支持。

| 状态 | 含义 | 终止 |
|---|---|---|
| PROPOSED | agent 提出调用请求（每次重新尝试也从这里开始） | 否 |
| AWAITING_APPROVAL | 需要审批，暂无有效审批 | 否 |
| AUTHORIZED | Policy Gate 检查通过 | 否 |
| INTENT_RECORDED | 已写意图记录（仅有副作用的调用） | 否 |
| EXECUTING | 执行中 | 否 |
| IN_DOUBT | 有副作用，结果不明 | 否 |
| SUCCEEDED | 执行完成，输出结构与后置条件通过（包括经对账确认已生效的情况） | 是 |
| POSTCONDITION_FAILED | 执行完成，后置条件未通过 | 是 |
| FAILED_NO_EFFECT | 失败，且能确定没有产生副作用 | 重试用完后为终止 |
| DENIED | 被 Policy Gate 拒绝，或审批被拒绝、作废 | 是 |

```
PROPOSED ─┬─▶ DENIED
          ├─▶ AWAITING_APPROVAL ─┬─▶ AUTHORIZED
          │                      └─▶ DENIED（审批被拒或作废）
          └─▶ AUTHORIZED ─┬─▶ EXECUTING（无副作用）
                          └─▶［E 级：核对基础版本，不一致 → DENIED］─▶ INTENT_RECORDED ─▶ EXECUTING

EXECUTING ─┬─▶ SUCCEEDED / POSTCONDITION_FAILED
           ├─▶ FAILED_NO_EFFECT ─▶（max_attempts 内）PROPOSED，作为新的尝试
           └─▶ IN_DOUBT ─┬─▶ 对账确认已生效 ─▶ SUCCEEDED / POSTCONDITION_FAILED
                         ├─▶ 对账确认未生效 ─▶ FAILED_NO_EFFECT
                         └─▶ 无法判断 ─▶ 保持 IN_DOUBT，任务进入 BLOCKED(in_doubt)
```

### 6.6 粒度、重试与检查点

| 项目 | 规定 |
|---|---|
| 重试预算 | 步骤级：`max_attempts`，每次重试是同一步骤下的新尝试记录，并重新经过 Policy Gate。任务级：`max_replans`（VERIFYING 失败后重新规划的次数），以及第 13 节的预算 |
| 检查点 | 每个步骤到达终止状态时创建；任务离开 RECORDING 时创建 |
| 恢复粒度 | 步骤：已终止的步骤不再执行；未终止的步骤按第 9.4 节第 6 步处理 |
| E 级审批的消耗 | 一次性审批在写入意图记录时消耗；之后的任何重试都需要新的审批 |

| `side_effects` | none / writes_store / displays（S 级展示）/ writes_cad |
| `idempotent` | 重复执行是否安全 |
| `base_scope` | 写入 CAD 的工具必须声明目标对象及其依赖对象（例如 margin line 所在的预备体网格），用于审批绑定（第 10.3 节） |
| `postconditions` | 工具特定的结果检查（例如几何工具必须返回对应状态） |
| `timeout`、`error_codes` | 超时与错误代码；必须区分「请求未被执行」与「结果不明」 |

**Research Browser 集成**

- Research Browser 的专用工具契约、公开网页抓取约束、挑战暂停/人工恢复、证据字段和 RB-01–RB-15 验收项见 [06 · Research Browser MCP 集成规范](06-research-browser-mcp.md)。
- 该工具组 MVP 只允许 `tier = R`、`side_effects = none`，且只在 `offline-research` 模式注册；远程 provider 默认关闭。MCP 只提供传输与工具发现，不能替代本 Runtime 的 Tool Registry 或 Policy Gate。
- 遇到 CAPTCHA、登录要求、速率限制或站点策略阻挡时，必须按第 6.4 节进入 `BLOCKED(human_feedback)` 或适用的预算/策略阻塞状态；模型消息本身不能充当可信人工验证记录。恢复必须走事件日志，并重新执行策略和版本检查。

### 7.2 调用协议

1. agent 提出调用请求：工具、版本、参数。
2. Policy Gate 检查：工具在当前模式已注册，级别、数据分区、外发、预算均允许；S 级展示还要通过质量闸门（第 10.7 节）；E 级还要有效审批（第 10.3 节）。
3. E 级调用：读取目标对象及其依赖对象的当前版本，与审批中的基础版本比较，一致才继续。
4. 有副作用的调用：写**意图记录**（参数、预期效果、执行前版本快照 ID）。E 级审批此时被消耗。
5. 执行。CAD 接口支持条件写入时，E 级调用必须使用条件写入（版本不变才写入）。
6. 校验输出结构与后置条件。
7. 写**完成记录**（ToolCall）：工具版本、输入引用与哈希、输出引用与哈希、耗时、状态、尝试次数。
8. 把结果返回给 agent。结果是数据，不是指令（I11）。

### 7.3 错误、结果不明与对账

只有以下情况可以认定「没有产生副作用」：

- 工具声明 `side_effects = none`；
- 错误发生在执行之前（输入校验、策略检查、审批检查、基础版本核对）；
- 工具以明确的错误代码报告请求未被执行。

其他情况一律视为**结果不明**。

| 情况 | 步骤状态 | 后果 |
|---|---|---|
| INVALID_INPUT（执行前） | FAILED_NO_EFFECT | 任务回到 PLANNING |
| POLICY_DENIED | DENIED | 任务回到 PLANNING；同一请求被拒次数超过阈值时，进入 BLOCKED(human_feedback) |
| NEEDS_APPROVAL | AWAITING_APPROVAL | 任务进入 BLOCKED(approval) |
| BASE_VERSION_CHANGED（执行前核对不一致） | DENIED | 审批作废；任务回到 PLANNING，基于新版本重新生成并验证候选，再申请新的审批 |
| DATA_UNAVAILABLE（执行前） | FAILED_NO_EFFECT | 任务进入 BLOCKED(missing_evidence) |
| 无副作用工具的 TIMEOUT、TOOL_ERROR、进程终止 | FAILED_NO_EFFECT | 在 `max_attempts` 内重试；用完则任务回到 PLANNING 或 FAILED |
| 有副作用工具明确报告「未执行」（包括条件写入因版本变化被拒） | FAILED_NO_EFFECT | 可以重试；E 级需要新的审批；条件写入被拒时同时视为基础版本变化 |
| 有副作用工具的 TIMEOUT、TOOL_ERROR、连接中断、进程终止 | IN_DOUBT | **先对账**；查清之前不得重试，也不得判定失败 |
| 无副作用工具的 POSTCONDITION_FAILED | POSTCONDITION_FAILED | 进入任务 VERIFYING 的失败分支 |
| 有副作用工具的 POSTCONDITION_FAILED | POSTCONDITION_FAILED | 副作用已经发生：任务进入 BLOCKED(human_feedback)，附回滚建议；回滚本身是 E 级动作（04 §4） |

**对账**

- 非幂等工具，以及所有 E 级调用：用只读工具查询外部状态（例如读取 CAD 当前版本），与意图记录中的预期效果比较。
  - 已生效：按成功处理，再检查后置条件；
  - 未生效：转为 FAILED_NO_EFFECT，可以重试（E 级需要新的审批）；
  - 无法判断：保持 IN_DOUBT，任务进入 BLOCKED(in_doubt)，由人工确认。
- 幂等、非 E 级的工具：可以用重试完成对账，因为重复执行与执行一次等效；完成记录标明经过对账重试。
- 不支持条件写入的 CAD 接口：E 级写入后必须立即读取结果版本并对账；发现执行期间有其他修改时，进入 BLOCKED(in_doubt)。

### 7.4 非确定性工具与重放

模型调用等非确定性工具必须记录以下内容，用于审计和重新执行：

| 项目 | 说明 |
|---|---|
| 模型 ID 与版本 | — |
| 系统提示版本 | 及其完整内容的引用 |
| 完整输入的引用 | 发给模型的全部消息内容；受权限保护；含患者派生数据时，按第 10.5 节加密并记录 lineage |
| 工具定义及版本 | 提供给模型的工具定义 |
| 调用参数 | 温度等采样参数、最大长度、随机种子（如支持） |
| 外部工具输出的引用 | 作为输入一部分提供给模型的工具结果 |
| 完整输出的引用 | — |

- 哈希只用于完整性校验，不能代替内容。
- 不保存、也不依赖模型的内部推理过程作为审计记录；需要的是可审计的输入、版本与输出。

两种重放必须区分：

- **忠实重放**（审计用）：只读取原始输入和已记录的非确定性输出；其后的确定性步骤**重新执行**，并独立计算指标；结果必须与原始记录一致（或在声明容差内）。重放不得读取原先记录的确定性中间结果或指标，否则只是重新读取，不是重放。
- **重新执行**（回归用）：用指定版本重新调用非确定性工具；与原始运行的差异单独报告，不覆盖原记录。

### 7.5 Predictor

Predictor 是 `kind = predictor` 的工具：

- 必须：参与 [03](03-experiment-protocol.md) 评估的 Predictor 在评估前冻结版本与参数（例如 M 的相似度特征、`k`、聚合方式，见 03 §5.1）。
- 必须：Predictor 读取历史时经过 Memory Manager，受第 8.3 节的时间与来源边界约束。
- 必须：评估运行中，Predictor 只在密封区内运行：可以读取当前测试病例的输入，以及第 8.3 节边界允许的历史；不能写入密封区之外的任何存储（包括检索索引和缓存），也不能外发（第 10.8 节）。

## 8. 记忆分层 【新增；Record Store 中的对象沿用 02】

### 8.1 四层记忆

| 层 | 内容 | 写入者 | 可变性 | 是否受压缩影响 |
|---|---|---|---|---|
| Evidence Store | CAD 导出、STL、操作事件、工具输入输出负载、人工反馈原文 | 适配器、工具、人工 | 只追加；内容寻址 | 否 |
| Record Store | 02 的 Case / Session / Episode / GD / CE / VI；Observation、DecisionRecord、QualityResult、Conflict、工作假设 | 确定性工具、人工；agent 只能写 Observation、DecisionRecord 与工作假设 | 只追加；以新记录取代旧记录 | 否 |
| Working Memory | 当前目标、计划、未完成步骤、未决假设列表、最近结果的引用、预算余量 | Runtime 从事件日志与 Record Store 投影生成 | 随时可以重建 | 是（压缩的唯一对象） |
| Knowledge Store | 跨病例总结、偏好描述、适用条件、反例 | agent 提议；状态由 Evaluation Harness 更新 | 带版本，只能以新版本修改 | 否 |

- 必须：从网格推导出的曲线、特征等属于 Record Store 中的派生记录，必须标明推导算法及其版本。它们不是原始证据，不能当作牙技师所定曲线的标签。
- 必须：含患者派生数据的模型输入（第 7.4 节）、检索索引、嵌入向量等，同样记录 lineage，纳入受控删除（第 10.5 节）。

### 8.2 KnowledgeItem

| 字段 | 内容 |
|---|---|
| `item_id`、`version` | 标识与版本 |
| `statement` | 知识内容 |
| `scope` | 适用条件（牙技师、牙位、修复类型等） |
| `status` | CANDIDATE / VALIDATED / DEPRECATED，与对应工作假设的状态联动 |
| `supporting`、`contradicting` | 支持与反对证据的引用 |
| `lineage` | 来源病例假名 ID、来源患者假名 ID、来源数据的最晚时间、来源数据分区 |
| `derived_by` | 生成者（agent、模型、工具及其版本） |

- 必须：新证据与 VALIDATED 条目矛盾时，追加到 `contradicting`，并创建冲突记录；不能静默修改或删除条目。
- 必须：DEPRECATED 条目保留，只是不再被默认检索。

### 8.3 读取边界（防泄漏）

每次记忆查询必须带上：

| 参数 | 含义 |
|---|---|
| `as_of` | 只返回来源数据全部早于该时间的条目 |
| `exclude_patients` | 排除来源包含这些患者（假名 ID）的条目 |
| `partitions` | 允许的数据分区 |

- 必须：Evaluation Harness 对测试病例 `c` 运行时，`as_of` 设为 `c` 的时间，`exclude_patients` 包含 `c` 的患者（与 [03](03-experiment-protocol.md) §2、§5.1 一致）。
- 必须：条目的来源中只要有一部分不满足边界，整个条目都不返回，不能部分使用。
- 必须：每次 Knowledge Store 读取都记录查询参数与返回的条目，供泄漏审计。
- 必须：评估运行产生的记录（逐病例预测、误差、中间结果）只写入密封区，不进入 Record Store 的一般视图，也不进入 Knowledge Store（第 10.8 节）。

## 9. 上下文压缩与恢复 【新增】

### 9.1 原则

- 压缩只作用于模型上下文（Working Memory 的呈现），不触及 Evidence Store、Record Store 和 Knowledge Store。
- 压缩的产物是**上下文摘要**：可以重新生成的派生物，不具有权威性。权威的是存储。
- 检查点由 Task & State Manager 创建（第 6.6 节），与压缩分开。压缩可以引用检查点，但不能生成或改写检查点。

### 9.2 上下文摘要

| 部分 | 内容 | 生成方式 | 权威性 |
|---|---|---|---|
| 结构化部分 | 任务与步骤状态、未完成步骤、未决假设及其状态、待审批、未解决冲突、预算余量、关键证据引用 | 从存储确定性生成 | 与存储一致即可信 |
| 叙述部分 | 当前思路、下一步打算 | 模型撰写 | 非权威；每条陈述必须引用证据或记录，没有引用的陈述标为「未核实」 |

- 必须：审批状态只出现在结构化部分，且来自审批存储。叙述部分出现的「已批准」不产生任何权限（I4）。

### 9.3 检查点

| 字段 | 内容 |
|---|---|
| `checkpoint_id`、`seq`、`snapshot_hash` | 标识、对应的事件序号、快照哈希 |
| `task_id`、`case_ids`、`timestamp` | 范围与时间 |
| `state` | 任务状态、各步骤状态与尝试次数 |
| `open_hypotheses` | 未决工作假设及其状态 |
| `evidence_refs` | 关键证据引用 |
| `tool_call_refs` | 已完成工具调用的引用 |
| `in_flight` | 处于 INTENT_RECORDED、EXECUTING 或 IN_DOUBT 的步骤 |
| `versions` | 工具、模型、策略、数据分区定义、登记记录的版本 |
| `digest_version` | 对应的上下文摘要版本 |
| `revalidate` | 恢复后需要重新验证的事项 |

审批不是检查点的权威内容，恢复时从审批存储重新读取。

### 9.4 恢复流程

1. **找检查点**：选择最近一个快照哈希校验通过、且从它到日志末尾完整性校验也通过的检查点。
2. **重建状态**：加载快照，回放其后的事件。
3. **核对证据**：所有被引用的证据都必须能找到且哈希一致；缺失时，相关步骤进入 BLOCKED(missing_evidence)。
4. **重读审批**：从审批存储重新读取；已过期、已撤销、已用完或作废条件成立的审批（第 10.3 节）都不再有效，相关步骤回到 AWAITING_APPROVAL。
5. **检查版本漂移**：工具、模型、策略、数据分区定义或登记记录与检查点记录不同时：
   - 属于预登记评估运行的任务：进入 BLOCKED(drift)，不能用新版本继续，否则评估无法复现；
   - 探索性任务：记录漂移事件，之后的结果标注新版本，可以继续。
6. **处理未终止的步骤**（第 6.5 节）：
   - PROPOSED、AWAITING_APPROVAL、AUTHORIZED：重新经过 Policy Gate 检查后继续；
   - 无副作用、处于 EXECUTING：视为 FAILED_NO_EFFECT，在预算内重试；
   - 有副作用、处于 INTENT_RECORDED、EXECUTING 或 IN_DOUBT：视为 IN_DOUBT，按第 7.3 节对账，**不能自动重试**。
7. **重建上下文**：从存储重新生成上下文摘要的结构化部分，与压缩前的结构化部分逐项比较，必须一致。
8. **继续**：从最近的安全状态继续。

### 9.5 压缩时机

- 应当：在步骤边界压缩，不在工具调用进行中压缩。
- 可以：在上下文接近容量时、或长时间等待人工之前压缩。

## 10. 权限、审批与数据治理 【R / S / E 已定义于 04 §2；其余新增】

### 10.1 Policy Gate

- 必须：用确定性代码实现，不调用模型做权限判断。
- 必须：策略配置有版本，存放在模型无法写入的位置；策略变化本身是事件。
- 必须：所有工具调用都经过 Policy Gate，没有旁路。

### 10.2 运行模式、权限级别与审批语义

运行模式见第 4 节，权限级别见 [04](04-risk-and-governance.md) §2。

| 级别 | 是否改变 CAD | 是否需要审批 | 附加条件 |
|---|---|---|---|
| R | 否 | 否 | — |
| S | 否；只读的建议输出 | 否 | 只有通过质量闸门的候选才能以可采纳的形式展示（第 10.7 节） |
| E | 是 | 是；每次执行都需要牙技师对该候选的明确批准 | 审批绑定候选及其基础版本（第 10.3 节） |

- 执行批准不等于放行最终设计。最终设计由牙技师在 CAD 中自行确认；Runtime 没有任何确认或放行最终设计的工具。

### 10.3 审批

**审批范围**

| 字段 | 内容 |
|---|---|
| `approval_id` | 标识 |
| `approver` | 经过身份验证的人工 ID；agent 不能写审批 |
| `target` | 病例、会话、CAD 对象 |
| `base_version` | 候选生成时，目标对象及其依赖对象（工具声明的 `base_scope`）的版本 ID 与内容哈希 |
| `candidate_hash` | 候选几何的哈希 |
| `provenance` | Predictor、Geometry Engine、执行工具的 ID 与版本；参数哈希 |
| `quality_gate` | 质量闸门结果的引用，及所用闸门标准集的版本 |
| `policy_version` | 审批时的策略版本 |
| `granted_at`、`expires_at` | 授予与过期时间 |
| `uses` | 允许使用次数；E 级必须为 1 |
| `revoked_at` | 撤销时间（如有） |

**作废条件**（任一成立即作废）

- 已过期、已撤销或已用完；
- 候选几何、参数，或 `provenance` 中任何版本发生变化；
- 目标对象或依赖对象的当前版本与 `base_version` 不同，**即使候选哈希没有变化**；
- 闸门标准集版本或策略版本发生变化；
- 执行请求的目标与 `target` 不一致。

**执行前核对**

- 必须：E 级执行前，用只读工具读取目标对象与依赖对象的当前版本，与 `base_version` 比较；不一致即拒绝执行并作废审批，基于新版本重新生成和验证候选，再申请新的审批。
- 必须：CAD 接口支持条件写入时使用条件写入；不支持时，写入后立即对账（第 7.3 节）。这项接口能力在 Phase 3a 审计。
- 依赖范围之外的对象变化不使审批作废；无法确定依赖范围时，以整个病例的版本作为基础版本。
- 必须：审批通道独立于模型对话；模型转述的批准不算审批。
- 审批人与有效期待定（Q17）。

### 10.4 数据分区

| 分区 | 内容 | Research Engine | Predictor（评估运行中） | Evaluation Harness |
|---|---|---|---|---|
| dev | 开发数据 | 可读 | 按第 8.3 节的边界读取 | 可读 |
| calib | 阈值与分界值的校准数据（例如 03 §4.2 的校准子集） | 可读，仅用于校准任务 | 否 | 可读 |
| holdout | 留出评估数据（03 的测试病例、H1 评估子集） | **不可读**（输入与标签都不可读） | 只读当前测试病例的输入 | 仅在密封评估运行中可读 |
| review | 专家质量复核结果 | 不可读其中属于 holdout 的部分 | 否 | 可读 |

- 必须：越权读取被拒绝并记录。
- 必须：参数校准只在 calib 上进行；holdout 不参与任何参数调整。
- 必须：留出评估只能通过密封评估通道进行（第 10.8 节）。
- 必须：shadow 运行产生的数据在登记时指定分区；计划用于确认性评估的，按 holdout 处理。

### 10.5 患者数据、假名化与受控删除 【术语与保管方式见 04 §1；待决：Q5、Q10、Q16、Q19】

**做法**

- 本项目默认采用**假名化**：数据进入 Evidence Store 之前去除直接标识符，以患者假名 ID 和病例假名 ID 代替。映射表由数据提供方或独立托管人保管，Runtime 不能访问。假名化数据仍按个人数据管理（04 §1）。
- 必须：按患者的撤回或删除请求，由映射表保管方转换为患者假名 ID 后提交；Runtime 不接触真实身份。
- 应当：证据负载按患者密钥加密存储；内容寻址使用密文的哈希或带密钥的哈希，避免用明文哈希确认某份网格是否在数据集中。
- 必须：事件日志不内嵌患者数据负载，只保存引用；否则销毁密钥也无法删除日志中的内容。

**删除覆盖的层次**

| 层次 | 删除动作 | 验证方式 |
|---|---|---|
| 证据负载 | 删除密文，销毁患者密钥 | 读取失败 |
| 密钥 | 销毁密钥及其备份 | 密钥管理记录 |
| 备份与副本 | 备份同样按患者密钥加密，密钥销毁后不可读；按保留政策轮换清除 | 从备份恢复演练后，该患者的数据不可读 |
| 缓存与索引 | 清除 Working Memory、上下文摘要、检索索引、嵌入向量中的相关内容并重建 | 检索不返回该患者的派生内容 |
| 派生记录 | 按 lineage 找出 Record Store 中的派生记录，按保留政策删除或重新计算 | lineage 查询为空，或记录已标记 |
| Knowledge Store | 来源含该患者的条目失效，按需重新生成 | 同上 |
| Predictor 版本 | 按保留政策重新训练、停用，或保留并标注（待决：Q16） | 版本登记中有对应标记 |
| 外发副本 | 按数据处理协议要求接收方删除 | 协议与删除确认记录 |
| 事件日志 | 写入删除事件（墓碑）；日志完整性不受影响 | 完整性校验通过 |

- 只写墓碑不等于完成删除；是否完成，以上表各层的验证结果为准。
- 必须：真实患者数据进入 Phase 3b 之前，至少确定临时的保留期限与撤回流程（Q16）。

### 10.6 外发控制 【待决：Q14、Q15】

调用 Runtime 之外的服务（例如外部模型 API）就是数据外发。

| 数据类别 | 例子 | 默认 |
|---|---|---|
| 合成数据 | 测试夹具 | 允许 |
| 去标识的结构化数据 | GD 描述符、统计量、任务状态 | 按数据处理协议决定 |
| 去标识的几何 | 网格、曲线 | 默认不允许 |
| 原始或可能可识别的数据 | 原始扫描、订单信息 | 不允许 |

- 必须：Policy Gate 按工具注册的 `egress` 信息和数据类别检查每次外发；未声明的外发一律拒绝。
- 允许外发的范围由部署方式与数据处理协议决定。

### 10.7 质量闸门 【新增；与 01 §5 统一】

运行时的质量闸门使用登记的**闸门标准集**：确定性、可自动执行的几何检查，包括 [03](03-experiment-protocol.md) §7.2 的硬性失败条件。专家复核属于离线的 Quality Validation，不在运行时闸门内。通过闸门只是展示与执行的必要条件，不代表临床或制造质量合格。

候选**通过闸门**的条件：闸门标准集中的每一项都有结果，并且每一项都是 `evaluation_validity = 可评价`、`quality_result = 通过`。缺少任何一项结果，都视为未通过。

| 输出类型 | 通过闸门 | 未通过、未评价、不可评价或结果缺失 |
|---|---|---|
| 质量检查报告、失败原因、相关证据 | 可以展示 | 可以展示 |
| 区域提示（例如「这一区域符合你的修改习惯，但候选未通过 X 检查」） | 可以展示 | 可以展示，不附候选几何 |
| 作为可采纳修改方案的候选几何 | 可以展示（S 级） | 不展示 |
| 写入 CAD | 经审批后可以执行（E 级） | 禁止 |
| 偏好符合程度 | 可以记录与展示 | 可以记录；不能改变闸门结论 |

- 依据区域的对应状态为 AMBIGUOUS 或 UNMATCHED 时，只给区域提示，不给逐点位移（01 §5）。
- 闸门是 Policy Gate 的一部分，用确定性代码实现。

### 10.8 密封评估通道 【新增】

留出评估在密封区中运行，防止评估结果通过任何途径回流到 Research Engine。

**启动与配置**

- 必须：评估运行只能由项目负责人按登记的评估配置发起，由 Evaluation Harness 执行。配置包括：冻结的 Predictor 版本与参数、测试病例集、指标、预登记的分组及最小分组规模、输出内容。
- 必须：Research Engine 不能发起、暂停、重跑或修改评估运行。
- 必须：同一配置在同一留出集上的运行次数有上限（默认 1 次）。因技术故障重跑时须记录原因，所有运行都要报告。

**留在密封区内的内容**

- 留出病例的输入与标签；
- 逐病例的预测、误差明细和中间结果（例如检索到的邻居、特征值）；
- 评估运行的日志与错误详情。

具体要求：

- 必须：评估运行的事件写入密封日志；一般事件日志只记录运行摘要：运行 ID、配置版本、状态。
- 必须：返回给 Research Engine 的错误只有运行级的状态代码，不含病例细节。
- 必须：评估期间，Predictor 不能写入密封区之外的任何存储，也不能外发（第 7.5 节）。

**输出**

- 必须：评估结束后，只按登记的输出内容发布汇总指标和审计报告。分组汇总只限预登记的分组，且每组病例数不少于登记的下限；不接受临时分组。
- 逐病例信息只有经授权的人员可以访问，且须在评估结论锁定之后，用于失败分析。
- 必须：逐病例信息一旦被用来修改 Predictor、工作假设或检索策略，该留出集即视为已消耗，降级为开发数据；之后的确认性评估需要新的留出数据。每个留出集的使用次数与消耗状态都要记录，并在报告中披露。

## 12. 冲突处理 【新增；各类解决规则沿用 02、03】

| 冲突类型 | 例子 | 预定的解决规则 |
|---|---|---|
| 专家意见不一致 | 两位复核专家结论不同 | 03 §7.4：第三位裁定，或登记的替代流程 |
| 对应路径不一致 | 相邻对应与直接对 `S_0` 对应的位置不同 | 02 §6.3：标为 AMBIGUOUS，不选真值 |
| 规则与人工标签不一致 | 去向规则的输出与人工标注不同 | 03 §4.2：以人工标签为准，记录差异 |
| 知识与新证据矛盾 | VALIDATED 条目遇到反例 | 第 8.2 节：追加反例；超过阈值时创建重新评估任务 |
| 数据或版本不一致 | 引用的几何版本哈希不匹配 | BLOCKED(missing_evidence) |

- 必须：冲突是独立记录，状态为 OPEN / RESOLVED，包含相关条目、检测者、解决规则、解决者和解决依据。
- 必须：模型不能自行解决冲突。它可以提出解决建议，建议作为记录保存，由预定规则或人工执行。

## 13. 预算与停止条件 【新增】

每个任务登记预算：

- 最大循环轮数、`max_replans`、工具调用次数、运行时间、计算成本；
- 同时未决的工作假设数量上限。

| 停止条件 | 结果 |
|---|---|
| 任一预算耗尽 | BLOCKED(budget)，附报告 |
| 连续 N 轮没有新证据 | 结束本轮研究，未决假设标为 INCONCLUSIVE，附报告 |
| 同一请求反复被策略拒绝 | BLOCKED(human_feedback) |
| 检测到冲突 | BLOCKED(conflict) |

- 必须：预算上限由部署配置给出，模型不能修改（I3）。

开发阶段 Phase 0–4 与实验协议的阶段 1–3 不是同一套编号。完成某个开发阶段，不代表任何研究假设得到验证。

| Phase 3b · 真实病例 shadow | 在真实会话旁路运行 shadow 模式，只读 | Phase 2、3a 退出；Q5、Q10、Q11、Q14、Q15、Q19 已决；Q16 至少有临时的保留与撤回方案；AT-13 通过；shadow 数据的分区已登记 | 只读运行稳定，无外发违规 |
| Phase 4 · Supervised Assistance | 先 assist（S 级），后 assist-execute（E 级） | 相关评估结果支持（03 阶段 3）；Q17 已决；适配器支持版本查询，以及条件写入或写后对账；AT-07b、AT-18 在测试部署中通过 | 待定 |

Phase 1 的范围：

- STL 格式只存三角网格，不包含 margin line 曲线、编辑事件或中间版本（除非另有导出）。因此 Phase 1 验证的是 **Runtime 本身**（恢复、压缩、追溯、权限、隔离），**不能**检验 H1–H4。
- 即使 STL 同时包含初始与最终网格，也不意味着存在 margin line 曲线。只要学习目标仍是 margin line 的区域与局部位移，就必须另行确认曲线有可验证的导出来源；从网格推导出的曲线是派生记录（第 8.1 节），不能当作原始证据（Q18）。
- H1 的主要终点仍待 Q13 决议。Runtime 只按登记记录运行，不把当前的 H1 方案固化为前提（第 5.3 节）。
