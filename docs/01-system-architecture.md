# 01 · 系统架构说明

版本：v0.3 草案

v0.3 变更：Runtime Harness 的详细契约移至 [05 Agent Runtime 规范](05-agent-runtime-spec.md)；「预测 / 推理层」在 05 中拆为 Research Engine 与已注册的 Predictor。

v0.2 变更：决策记录中的单一置信度拆分为个人偏好与质量验证两项；明确推荐排序规则；暂停扩展算法路线。

## 1. 总体结构

架构明确区分两个 harness，以及它们服务的核心能力层。

```
              ┌──────────────────────── Evaluation Harness ────────────────────────┐
              │  固定测试集 · 历史重放 · 对照实验 · 回归测试 · 失败分析            │
              └───────────────────────────────▲────────────────────────────────────┘
                                              │ 记录与指标
┌────────────┐   ┌──────────────────── Runtime Harness ───────────────────────────┐
│ CAD 软件   │◀─▶│ 任务状态 · 工具注册与校验 · 记忆检索 · 人工批准 · 回滚 · 审计  │
│ (采集/执行)│   └──────┬──────────────┬───────────────┬──────────────┬────────────┘
└────────────┘          │              │               │              │
                  ┌─────▼────┐   ┌─────▼─────┐   ┌─────▼─────┐  ┌─────▼──────┐
                  │ 数据层   │   │ 几何引擎  │   │ 经验库    │  │ 预测/推理层│
                  │ 病例/会话│   │ (确定性)  │   │ (检索)    │  │ (候选方案) │
                  └──────────┘   └───────────┘   └───────────┘  └────────────┘
```

## 2. Runtime Harness · 运行时控制层

负责让 AI 按正确顺序、在正确权限内完成任务：

- 任务拆分与状态管理
- 工具注册、调用参数与结果验证
- 病例版本、历史记录与记忆检索
- 人工批准、失败恢复和修改回滚
- 记录每次建议的证据与结果

详细契约（不变量、运行模式、状态模型、工具契约、记忆分层、上下文压缩与恢复、权限与数据治理、验收测试）见 [05 Agent Runtime 规范](05-agent-runtime-spec.md)。

## 3. Evaluation Harness · 实验评估层

负责判断系统是否真的在进步，而不是感觉上更智能：

- 固定病例测试集与历史版本重放
- 预测准确性和几何质量评分
- 人工基线、相似案例和 AI 预测的对照实验
- 回归测试、失败分析与结果汇总

评估对象是整个「模型 + 工具 + 执行状态」系统，而不是语言模型的单次回答。

## 4. 各层职责边界

| 层 | 负责 | 不负责 |
|---|---|---|
| 数据层 | 存储病例、会话、片段、几何版本、反馈；版本与匿名化 | 判断修改是否正确 |
| 几何引擎 | 坐标变换、曲线对应、位移场、网格与曲线检查（确定性） | 决定该改哪里 |
| 经验库 | 按病例特征与区域检索历史修正 | 生成新几何 |
| 预测/推理层 | 组织任务、提出候选修改、给出证据与置信度；在 05 中拆为 Research Engine 与已注册的 Predictor | 直接写入最终几何；绕过验证器 |
| Runtime Harness | 调度、权限、审批、回滚、审计 | 评价系统长期效果 |
| Evaluation Harness | 离线与在线评估、回归 | 运行时决策 |

关键约束：**几何生成与 AI 推理分离**。语言模型负责任务组织、案例说明和候选方案管理；三维几何计算、坐标变换、曲线验证和网格检查由确定性算法完成。将来即使用学习模型生成候选几何，也必须通过独立验证器。

## 5. 可验证的决策记录

AI 每次建议修改时，产生一条结构化决策记录：

| 字段 | 含义 |
|---|---|
| Observations | 观察到的网格特征、历史案例及操作状态 |
| Hypothesis | 怀疑当前设计哪里需要调整 |
| Evidence | 支持该建议的几何数据及历史案例 |
| Alternatives | 其他可能的修改方案 |
| Preference | Personal Preference Score：建议与这位牙技师过去修正习惯的符合程度，以及其不确定性 |
| Quality | Quality Validation：预定义几何检查和专业审核的结果（通过 / 未通过 / 未评价），附标准版本 |
| Correspondence | 所依据区域的曲线对应状态（MATCHED / AMBIGUOUS / UNMATCHED） |
| Verification | 人工确认或拒绝的结果 |

Preference 与 Quality 不能合并成一个「AI 置信度」。

**推荐规则（建议）**：

1. Quality 是闸门：未通过质量检查的候选不推荐给牙技师执行；可以作为「符合你的习惯，但未通过检查」的提示单独显示，并说明未通过的项目。
2. Preference 只在通过质量检查的候选之间排序。
3. 依据区域为 AMBIGUOUS 或 UNMATCHED 时，不给出逐点位移的建议，只提示区域。
4. 训练时同样分开：偏好模型只学习「会怎样改」，不把被保留的修改当作质量标签。

重点是保留可检查的依据、候选方案、工具调用记录和验证结果，而不是冗长的模型自我解释。系统应能指出具体区域、引用相似案例，并说明哪些检查尚未通过；证据不足时输出「无法可靠判断」。

## 6. 算法路线（逐层递进）

| 层级 | 方法 | 要验证的问题 |
|---|---|---|
| L0 | 原始轨迹、CAD 事件和几何差异分析 | 能否准确还原操作过程？ |
| L1 | 贝塞尔曲线、B 样条、轨迹特征提取 | 平滑、曲率和速度特征是否包含有效信息？ |
| L2 | 历史案例检索 | 相似病例能否提供可复用的修改参考？ |
| L3 | 传统机器学习或局部几何预测 | 能否预测需要修改的区域与大致方向？ |
| L4 | 专门的三维模型与操作序列模型 | 能否在未见病例中产生更可靠的候选修改？ |
| L5 | 经过验证的 CAD 辅助执行 | 能否降低时间成本且不降低质量？ |

设计决定：

1. **贝塞尔曲线是轨迹描述工具，不是个人经验模型。** 原始轨迹必须保留，不能只存拟合曲线；拟合可能丢失停顿、反向调整和细小修正。
2. **先做案例检索（L2），再训练模型。** 检索是清楚的对照基线，后续更复杂的方法必须证明相对它有额外价值。
3. 每一层进入下一层之前，都要在 Evaluation Harness 中有对应的结论。
4. **当前暂停扩展 L0–L5。** 优先固定学习目标、可观测性、对照实验和执行治理（见 [README](../README.md) 的优先级）。
